# Developer Tools

A frontend-only website of developer utilities. Every tool processes input in the browser; user input is never sent to a server or a third-party service.

## Setup

Requires Node.js 20.9 or later (developed on Node 22) and npm.

```bash
npm install
cp .env.example .env.local   # optional: set NEXT_PUBLIC_SITE_URL
npm run dev                  # http://localhost:3000
```

`NEXT_PUBLIC_SITE_URL` is the public base URL used for canonical links, Open Graph URLs, `robots.txt` and `sitemap.xml`. It defaults to `http://localhost:3000`, so set it for production builds.

## Stack

- Next.js 16 (App Router, Turbopack) and React 19
- TypeScript in strict mode
- Tailwind CSS 4, configured through CSS tokens in `src/app/globals.css`
- ESLint 9 with `eslint-config-next` (Core Web Vitals and TypeScript rules)

Runtime dependencies beyond the framework, each loaded on demand only by the tool that uses it:

- `terser`: JavaScript minification (Minifier)
- `csso`: CSS minification (Minifier)
- `parse5`: spec-compliant HTML parsing (Minifier)
- `sql-formatter`: SQL formatting for 13 dialects (SQL Formatter)
- `diff`: line and word diffs and unified patches (Diff Checker)
- `@cfworker/json-schema`: JSON Schema validation by interpretation, with no code generation or eval (JSON Schema Validator, run in a Web Worker)
- `markdown-it` and `dompurify`: Markdown rendering with raw HTML disabled, then HTML sanitizing (Markdown Editor); DOMPurify's SVG profile also sanitizes SVG before it is drawn as an image (SVG to PNG Converter)
- `@noble/hashes`: audited, dependency-free MD5, SHA-224, SHA-3 and RIPEMD-160, which Web Crypto does not provide; SHA-1 and SHA-2 use Web Crypto (Hash Generator)
- `entities`: WHATWG-compliant decoding of all 2,231 named HTML character references; already installed through `markdown-it` and `parse5` (HTML Entity Encoder & Decoder)
- `yaml` and `smol-toml`: maintained YAML 1.2 and TOML 1.0 parsers and serializers with no dependencies (YAML ↔ JSON ↔ TOML Converter)
- `mime-db`: the MIME type dataset behind `mime-types` and Express, about 24 KB gzipped (MIME Type Lookup)
- `bcryptjs`: maintained pure-JavaScript bcrypt that takes its salts from `crypto.getRandomValues` (Bcrypt Hash & Verify)
- `@zxcvbn-ts/core`, `@zxcvbn-ts/language-common` and `@zxcvbn-ts/language-en`: the maintained port of the zxcvbn password strength estimator and its dictionaries, about 850 KB compressed. The breach-lookup matcher, which makes network requests, is not installed (Password Strength Analyzer)

- `bowser`: maintained, MIT-licensed user-agent parser (User-Agent Parser). `ua-parser-js` 2.x was not used because it is AGPL-licensed
- `qrcode-generator`: QR code encoding with no dependencies; text is converted to UTF-8 first, because the library's default byte encoding keeps only 8 bits per UTF-16 unit (QR Code Generator)

Bundled data: `src/data/oui-vendors.json`, the IEEE Registration Authority's public MA-L, MA-M and MA-S registries (54,240 prefixes), generated by `scripts/build-oui-data.mjs` from the BSD-2-Clause-licensed `oui-data` package, whose licence text is embedded in the file and shown on the tool page. About 590 KB gzipped, loaded only when the MAC Address Vendor Lookup page imports it. Vendors are never looked up online; update the data by upgrading `oui-data` and running `npm run data:oui`.

Development-only: `oui-data` (source of the bundled vendor data), `vitest` and `jsdom` (unit tests, jsdom for DOM-based sanitizer and SVG tests), `@playwright/test` and `@axe-core/playwright` (browser and accessibility tests), and `jsqr` (decodes generated QR codes in tests to prove they scan).

Every other tool is implemented in `src/lib/tools/` without dependencies. The image tools draw with Canvas 2D and decode files with `createImageBitmap`; favicon.ico and the favicon ZIP are written by small tested functions in `favicon.ts` rather than a library. The security tools (HMAC, RSA key pairs, text encryption, TOTP, Basic Auth) use only the browser's Web Crypto API: AES-GCM, PBKDF2, HMAC and RSA-OAEP are never implemented in JavaScript here.

## Architecture

```

  app/              Routes, root layout, global styles, robots.ts, sitemap.ts, icon
    page.tsx              Homepage
    tools/page.tsx        Tool directory (/tools)
    tools/<slug>/         One static route per tool: metadata, page content and the tool
    categories/[slug]/    Category pages (/categories/<slug>)
  components/
    layout/         Site chrome: SiteHeader, HeaderSearch, DesktopNav, MobileNav, ThemeToggle, SiteFooter,
                    PageHeader, SkipLink
    seo/            JsonLd
    ui/             Primitives: Button (+ buttonClassName), Container, Field, Label, Hint, Notice,
                    FieldError, Input, Textarea, Checkbox, SegmentedControl, CopyButton,
                    Alert, Separator, TextLink, PasswordInput (masked secret field with Show/Hide),
                    FileDropField (file input with drop area and optional paste)

                    css-generators, token, hash, date-format, base-convert, base64-file,
                    html-entities, text-binary, data-format, list, mime, slug, obfuscate, ulid,
                    bcrypt, hmac, rsa, password-strength, text-encryption, totp, basic-auth,
                    shell (shared command tokenizer), curl, url-parse, html-editor, user-agent,
                    http-status, keycode, qr, svg-placeholder, git-cheatsheet, docker-compose,
```

- **Frontend only.** No API routes, server actions, database, authentication or external data services.
- **Server Components by default.** Pages and layouts render on the server or at build time for SEO. Only interactive tool UIs are Client Components (`"use client"`), and they keep processing in the browser.
- **Registry-driven routing.** Each tool gets an entry in `src/content/tools.ts` and a route at `/tools/<slug>`. Categories live in `src/content/categories.ts`; a category page exists only while at least one tool belongs to it. The homepage, directory, category pages, footer and sitemap all read from these two files.
- **Tool grid and filters.** The homepage and `/tools` share `ToolDirectory`: a tile grid with category filters. On `/tools` the selected category is mirrored to `?category=`, and the page is prerendered with the full list as a Suspense fallback, so every tool is in the static HTML.
- **Tool pages.** Each tool is a static route at `src/app/tools/<slug>/page.tsx` that renders `<ToolPage>` with its written content (`ToolPageContent`: explanation, example, notes, FAQs) and the interactive component. Static routes mean an unknown `/tools/<slug>` returns a real 404. `ToolPage` adds FAQPage structured data that mirrors the visible FAQs and links to related available tools.
- **Tool icons.** `ToolIcon` draws a colorful, emoji-style SVG for each tool on a 32×32 grid, so icons look the same on every platform and in both themes. Add an entry to `ToolIconName` and the icon map for each new tool.
- **Regex safety.** The Regex Tester runs patterns in a Web Worker (`regex.worker.ts`) and terminates it after 1 second, and the JSON Schema Validator does the same after 3 seconds (`runInWorker` in `src/lib/worker.ts`), so catastrophic backtracking cannot freeze the page.
- **Tool status.** Each tool has `status: "planned" | "available"`. Planned tools appear as "Coming soon" tiles without a link and are left out of the sitemap. Set a tool to `"available"` when its page ships.
- **Header search.** `HeaderSearch` in the shared header searches the tool registry in the browser (`src/lib/search.ts`): names, keywords, category names and descriptions, every query word required, ranked by where the words matched. Only available tools are listed. It is an ARIA combobox with a listbox popup (Arrow keys, Enter, Escape, a clear button and a live result count), opens with `/` outside text fields and Ctrl+K (⌘+K on Mac) anywhere except key-capturing areas, and collapses to a button below the `md` breakpoint. Queries are not sent, stored or put in the URL.
- **Navigation.** `mainNav` and `footerNav` in `src/config/site.ts` drive the header and footer. The header shows its links from the `md` breakpoint up and a disclosure menu below it; both are hidden while `mainNav` is empty.
- **Theming.** Light and dark themes come from CSS token overrides keyed on `data-theme` on `<html>`. The preference (system, light or dark) is stored in `localStorage` under `theme`, and an inline script in `<head>` (`themeInitScript` in `src/lib/theme.ts`) applies it before first paint, so there is no flash. Without JavaScript the site follows the OS setting.
- **Metadata.** The root layout sets defaults, a title template (`%s · Developer Tools`) and `metadataBase`. Pages export metadata built with `pageMetadata()` from `src/lib/metadata.ts`, which also sets the canonical URL.

## Conventions

- **Privacy:** never send user input over the network. Do not add analytics, logging or error reporting that captures tool input.
- **Styling:** use the design-token utilities (`bg-surface`, `text-muted-foreground`, `border-border`, `border-input`, `text-accent`, `max-w-page`, `px-gutter`) instead of raw Tailwind palette colors. Tokens adapt to both themes, so use `dark:` only when a token cannot express the difference. Keep the visual language plain: subtle 1px borders, small radii, no gradients, shadows or decorative animation.
- **Layout:** wrap page content in `<Container>` (`prose`, `default` or `wide`). Each page renders exactly one `h1`, usually via `<PageHeader>`.
- **Accessibility:** use semantic HTML, give every form control a `<Label>` and connect hints and errors with `aria-describedby`, keep visible focus styles, and respect `prefers-reduced-motion`. New colors must meet WCAG AA in both themes (4.5:1 for text, 3:1 for control borders).
- **Links and buttons:** use `<TextLink>` or a plain link for inline links. For a link that looks like a button, apply `buttonClassName()` to `<Link>` rather than nesting a `<button>`.
- **Privacy claims:** only describe how a tool handles data once the implementation backs it up; a badge or tagline is not evidence.
- **Components:** use named exports and PascalCase file names for components, and camelCase for utilities. Extend native element props (`ComponentProps<"button">`) so primitives accept standard attributes.
- **Logic:** put tool logic in pure functions under `src/lib/tools/`, separate from React components, so it is easy to test. Tools must never execute user input and must not store it (no localStorage, no URL parameters).
- **Adding a tool:** add the entry to `src/content/tools.ts` (as `"planned"`), build the logic in `src/lib/tools/`, the component in `src/components/tools/<slug>/` and the route in `src/app/tools/<slug>/page.tsx`, then set the status to `"available"`.
- **Dependencies:** add a package only when it is clearly necessary. No component, icon or animation libraries.
- **Imports:** use the `@/` alias for anything under `src/`.
- **Secrets:** take passwords, keys and secrets with `PasswordInput`, which turns off autocomplete, autocorrect and spellcheck (spellcheck services can send field contents off the device). Keep secrets in component state only, and cover each security tool with `watchForLeaks` in `e2e/helpers.ts`, which fails if a secret reaches storage, cookies, the URL, a request or the console, or if any request leaves the site's origin.
- **Untrusted HTML and code:** render user HTML only in sandboxed iframes without `allow-scripts` (see `html-editor.ts`), and run user JavaScript only through the benchmark sandbox (`benchmark.ts`): a worker inside a `sandbox="allow-scripts"` frame with an opaque origin, a `default-src 'none'` CSP and its network APIs removed.
- **React state:** wrap functions and classes loaded at runtime before storing them in state (`setLib(() => lib)`): React calls a function passed to a state setter as an updater.
- **Tool layout:** put settings in `ToolToolbar`, and the primary action directly under the input with `ActionBar` (primary action, then Clear or Reset grouped on the right, then status feedback). Wrap tools that have one main action in `ShortcutScope`, so Ctrl/⌘+Enter runs it from any field. Use `Notice` for standing warnings (title visible, details on request) and keep `Alert` for feedback about the current input. Generators show a first result on load, created in the browser after hydration. Every tool with input or settings offers Clear and/or Reset that restores its state in place; never reload the page or route (a unit test checks this). Text boxes are not resizable.
- **Tests:** give each module in `src/lib/tools/` a unit test next to it (`name.test.ts`) covering normal cases, invalid input and edge cases, and cover each tool's main workflow in `e2e/`. Unit tests run with `TZ=America/New_York` (set in `vitest.config.mts`) so daylight saving cases are deterministic. Browser tests use the locally installed Chrome (`channel: "chrome"`). Every tool page is checked with axe (WCAG 2 A/AA) in the light and dark themes and for horizontal overflow at 360 px (`e2e/ux.spec.ts`).
